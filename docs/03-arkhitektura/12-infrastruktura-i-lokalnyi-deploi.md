# 12 · Інфраструктура і локальний деплой

> **Kite** — документація поштової системи · v1.4 · затверджено · 14.11.2026

Код живе в десятках окремих репозиторіїв (5.6), а збирається все докупи тут: репозиторій-оркестратор `kite-infra` тримає один compose-файл із трьома профілями і тягне готові образи з GitHub Container Registry. Стенд піднімається `docker compose --profile <профіль> up`; профілі потрібні, щоб не тримати все запущеним одночасно. Повний стенд з'їдає орієнтовно 10–12 ГБ RAM, тому під час розробки сервіс, який правиш, запускаєш з IDE, а решту — в Docker.

## 12.3 Порядок старту і готовність

1. Інфраструктура: Postgres, Redis, Kafka, Mosquitto, MinIO — з healthcheck у compose.
2. Keycloak імпортує realm `kite` з файлу: ролі, клієнти OAuth для kite-web, kite-ops, kite-business, kite-mobile, тестові користувачі кожної ролі.
3. Сервіси стартують з `depends_on: condition: service_healthy`; кожен застосовує свої міграції сам.
4. Одноразовий контейнер `kafka-init` створює топіки (по 6 розділів, фактор реплікації 1).
5. Контейнер `seed` наповнює мережу і тестові дані (12.4).

## 12.4 Сид-дані

- **Мережа:** Python-скрипт бере список обласних центрів і великих міст, розставляє хаби, сортувальні центри, відділення й Kite Box поблизу центру міст і прив'язує їх до справжніх адрес через локальний Photon (зворотне геокодування).
- **Маршрутизація:** правила генеруються з ієрархії «точка → обласний СЦ → магістральний хаб → магістральний хаб → обласний СЦ → точка»; розклад рейсів — двічі на добу між хабами.
- **Люди:** тестові клієнти, бізнес-організація з API-ключем і по одному працівнику на кожну роль; паролі — у README.
- **Карти:** вирізка України у форматі PMTiles завантажується один раз скриптом `make tiles` (утиліта pmtiles, обрізка за межами країни); стиль карти — власний JSON у кольорах бренду.
- **Геокодер:** готовий дамп Photon для України, якщо доступний, або власна збірка з даних OpenStreetMap; без Photon працює лише вибір точки на карті.

| --------------------------------- | ---------------------------------------------------------------------------------- |
| make up / make up-full / make obs | Підняти профіль core / full / спостережуваність                                    |
| make seed                         | Перезалити сид-дані                                                                |
| make tiles                        | Завантажити й обрізати тайли України                                               |
| make pull                         | Підтягнути образи поточних версій із GHCR                                          |

## 12.6 Збірка, образи і версії

**Пайплайн репозиторію.** У кожного репозиторію свій GitHub Actions: лінт, юніт- і інтеграційні тести (Testcontainers), перевірка на сумісність зі схемами з `kite-contracts`, збірка образу й публікація в `ghcr.io/<організація>/<сервіс>`. Пайплайни не копіюються з репозиторію в репозиторій: кожен викликає спільний reusable-workflow із `.github`, тож правка в одному місці змінює збірку всім.

**Теги образів.** Кожна збірка з `main` публікує образ із тегом `sha-<короткий хеш>`; реліз додає `v<semver>`. Рухомий `latest` compose не використовує — лише закріплені теги, інакше стенд щоразу піднімається різним.

**Де записані версії.** У `kite-infra` лежить файл `versions.env` з тегом кожного образу, а compose підставляє їх як змінні. Цей файл — єдине місце, яке описує, з чого саме складається стенд; його історія в git і є історією складу системи.

**Як версія оновлюється.** Після публікації образу пайплайн сервіса відкриває у `kite-infra` pull request, який піднімає його рядок у `versions.env`. Мердж цього PR — і є «деплоєм» на стенд. Вручну те саме робить `make bump`.

**Локальна розробка.** Сервіс, який правиш, підмінюється файлом `docker-compose.override.yml`: замість `image:` у нього `build:` з шляхом до сусіднього клону (`make dev SERVICE=shipment-service`). Решта стенду лишається на образах із реєстру, тож локально тримати всі 27 репозиторіїв не треба — досить тих, які зараз правиш.

**Доступ.** Образи й пакети приватні в межах організації; стенд автентифікується в GHCR токеном із правом `read:packages`, а пайплайни публікують через вбудований `GITHUB_TOKEN`.
